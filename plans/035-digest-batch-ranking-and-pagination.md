## Why this matters

Weekly digest fan-out performs one ranking RPC and then one events-table hydration query per user, producing `2N+3` database round trips for `N` recipients and rebuilding shared candidate data repeatedly. Recipient preference, profile, and preferred-city reads are also unpaginated while PostgREST is configured with `max_rows = 1000`; users beyond that cap are silently omitted, and preferred-city rows can truncate personalization. This plan makes the ranking RPC return the event display fields the handler already needs and paginates every recipient-source read. It deliberately stops short of a multi-user batch-ranking RPC so the first optimization remains reviewable and behavior-preserving.

### Step 2: Paginate recipient preferences and chunk related reads

In `send-weekly-digest/index.ts`, replace unpaginated recipient-source reads with bounded loops:

- Notification preferences: keyset pagination ordered by `user_id`, pages of 1000, and `.gt("user_id", lastUserId)` after the first page. Continue until a short page. Detect a non-advancing cursor and fail rather than loop forever.
- Profiles: chunk `userIds` into groups of 500 and perform one `.in("id", chunk)` query per group.
- Preferred cities: chunk `userIds` into groups of 200 and perform one `.in("user_id", chunk)` query per group. The 200-user bound keeps up to five city rows each under the 1000-row server cap.

Accumulate into the same arrays/Maps and preserve existing query error handling and recipient filtering. Do not add a generic pagination abstraction unless an existing one already matches this exact Supabase chain.

**Verify**: a test fixture with more than 1000 preference rows processes every recipient; query-spy assertions show keyset pages and bounded profile/city chunks with no unpaginated read.
